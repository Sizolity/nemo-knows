## 1. 双层架构：灵魂与手册

LLM Wiki 的实现分两层，互不耦合但必须协同工作：

### 第一层：专家角色定义 (Expert Prompt)

**位置**：注入到每次对话的 `<expert_prompt>` 标签中

**职责**：定义"我是谁"——人格、使命、沟通风格、职业道德

```
角色：个人知识库管理专家（资深图书馆员人格）
人格：严谨、有条理、主动发现知识间的关联和矛盾
记忆：记住整个 Wiki 的结构、索引和变更历史
经验：见过知识因缺乏系统化管理而"遗忘"，也见过编译型知识库带来的复利效应
```

**包含内容**：

| 模块 | 说明 |
|------|------|
| Identity & Memory | 角色定位、人格特征、记忆范围 |
| Core Mission | Ingest / Query / Lint 三大操作的定义 |
| Wiki 架构规范 | 三层目录结构、页面模板、index.md / log.md 格式 |
| Critical Rules | 知识质量标准（不幻觉、必须引用、标注矛盾、增量更新） |
| 操作纪律 | raw/ 只读、每次都更新索引和日志、kebab-case 命名 |
| Communication Style | 中文为主、技术术语保留英文、主动建议 |
| Professional Ethics | 区分事实与推理、建议人工验证 |
| Workflow | Understand → Locate → Execute → Update → Report |
| Success Metrics | 交叉引用密度、矛盾标注质量、索引完整性、查询命中率 |

### 第二层：llm-wiki Skill（操作手册）

**位置**：`~/.workbuddy/plugins/marketplaces/experts/plugins/llm-wiki/skills/llm-wiki/SKILL.md`

**职责**：提供具体的可执行指令——默认路径、初始化脚本、工作流选择逻辑

```
关键信息：
- 默认 Wiki 根目录：~/.workbuddy/wiki-knowledge/
- 包含 init_wiki.sh 脚本用于初始化
- 包含工作流选择逻辑（触发词匹配）
- 可独立加载、可版本管理、可跨项目复用
```

### 为什么分两层？

```
Expert Prompt                      Skill
┌──────────────────────┐          ┌───────────────────┐
│ 哲学层 "为什么要这样做"  │  ──→  │ 操作层 "具体怎么做"   │
│ 人格、质量标准、边界      │      │ 路径、脚本、触发词    │
│ 每次对话都生效           │      │ 按需加载，可替换      │
└──────────────────────┘          └───────────────────┘
```

- **Expert Prompt** 负责"精神内核"——换了任何 LLM，只要加载这个 Prompt，行为模式一致
- **Skill** 负责"执行细节"——路径变了、脚本升级了，只改 Skill，不碰 Prompt
- 两层解耦意味着未来可以用不同的 Skill 驱动同一套 Expert（比如针对不同语言或不同存储后端）

## 2. 三层数据结构

```
{wiki_root}/
├── raw/              ← 第一层：原始资料（只读，用户投放）
│   ├── paper-xxx.md
│   ├── article-xxx.md
│   └── notes-xxx.md
├── wiki/             ← 第二层：LLM 编译维护的知识层
│   ├── index.md      ← 内容目录索引（唯一导航入口）
│   ├── log.md        ← 变更时间线日志（唯一信任根）
│   ├── entities/     ← 实体页面
│   │   ├── person-xxx.md      （人物）
│   │   ├── company-xxx.md     （公司/机构）
│   │   └── product-xxx.md     （产品/系统）
│   ├── concepts/     ← 概念页面
│   │   ├── concept-xxx.md     （理论概念——"是什么"）
│   │   └── method-xxx.md      （方法论——"怎么做"）
│   └── topics/       ← 主题综述页面
│       ├── topic-xxx.md       （领域综述）
│       └── comparison-xxx.md  （对比分析）
└── SCHEMA.md         ← 第三层：Wiki 规则配置文件
```

### 三层职责

| 层 | 目录 | 角色 | 谁操作 |
|----|------|------|--------|
| 原始层 | `raw/` | 不可变的事实来源 | 用户放入，LLM 只读 |
| 知识层 | `wiki/` | 编译后的结构化知识 | LLM 创建、更新、维护 |
| 规则层 | `SCHEMA.md` | 格式与约定的宪法 | 初始化时自动生成 |

### 页面分类体系

```
实体 (entities/)
  ├── person-*      人物：作者、研究者、引用者
  ├── company-*     机构：公司、实验室、大学
  └── product-*     产物：模型、工具、框架、数据集

概念 (concepts/)
  ├── concept-*     理论概念：定义、性质、原理（"是什么"）
  └── method-*      方法论：算法步骤、技术流程（"怎么做"）

主题 (topics/)
  ├── topic-*       领域综述：某个方向的整体视图
  └── comparison-*  对比分析：两个以上概念的横向对比
```

### 页面模板

每个 Wiki 页面遵循固定结构：

```markdown
# {页面标题}

> **类型**: entity | concept | topic | comparison
> **创建时间**: YYYY-MM-DD
> **最后更新**: YYYY-MM-DD
> **来源**: [[raw/source-file]]

## 摘要
{一段话概括核心内容}

## 详情
{详细内容，可包含多个子标题}

## 关联
- 相关实体: [[entity-xxx]], [[entity-yyy]]
- 相关概念: [[concept-xxx]]
- 参见: [[topic-xxx]]

## 引用来源
- [1] [[raw/paper-xxx.md]] — {引用说明}
- [2] [[raw/article-xxx.md]] — {引用说明}

## 变更记录
- YYYY-MM-DD: 初始创建，来源 [[raw/xxx]]
- YYYY-MM-DD: 更新 XXX 部分，来源 [[raw/yyy]]
```

### index.md 格式（唯一导航入口）

```markdown
# Wiki 索引

> 总页面数: {N} | 最后更新: YYYY-MM-DD

## 按类型

### 实体 ({n})
- [[entities/person-xxx]] — 简短描述
- [[entities/company-xxx]] — 简短描述

### 概念 ({n})
- [[concepts/concept-xxx]] — 简短描述

### 主题 ({n})
- [[topics/topic-xxx]] — 简短描述
```

### log.md 格式（唯一信任根）

```markdown
# 变更日志

## YYYY-MM-DD
- ✨ 新增: [[entities/xxx]] — 来源 [[raw/yyy]]
- 📝 更新: [[concepts/xxx]] — 新增了 ZZZ 部分
- 🔗 链接: [[entities/aaa]] ↔ [[concepts/bbb]]
- ⚠️ 矛盾: [[entities/xxx]] 与 [[entities/yyy]] 在 ZZZ 问题上存在分歧
```

## 3. 三大核心操作

### 3.1 Ingest（知识编译）

```
触发 → 用户放入 raw/ 新文件 → 请求编译

流程：
1. 读取 raw/ 新资料
2. 提取关键信息
3. 创建/更新 10-15 个 Wiki 页面
4. 建立 [[双向交叉引用]]
5. 更新 index.md + log.md
```

**关键约束**：一次只处理一份 raw 资料。编译质量靠深度理解，不靠吞吐量。

### 3.2 Query（智能查询）

```
触发 → 用户提问 → 基于 Wiki 内容回答

流程：
1. 读取 index.md 定位相关页面
2. 读取对应页面内容
3. 综合推理 + 标注引用来源
4. 有价值的答案归档为新页面
5. 飞轮效应：查询也增长知识库
```

**飞轮效应**：当查询产生了有价值的新洞察（对比分析、综合结论），主动将其归档为新的 Wiki 页面。这样查询本身也在扩大知识库。

### 3.3 Lint（健康巡检）

```
触发 → 用户请求 / 定期自动 → 全面扫描

巡检项目：
1. 扫描矛盾结论 → 检查不同页面是否存在对同一事实的冲突描述
2. 检测过时信息 → 找出时间敏感的结论（如"截至 2023 年..."）
3. 标记孤立页面 → 没有任何其他页面引用它的页面
4. 发现缺失引用 → 被多次提及但尚无独立页面的概念
5. 主动建议研究方向 → 基于现有知识图谱的空白
```

### 三大操作的产出物对比

| 操作 | 读取 | 写入 | 最少接触 | 最多接触 |
|------|------|------|----------|----------|
| Ingest | 1 份 raw | 10-15 个 wiki 页面 + index + log | 3 个文件 | 17 个文件 |
| Query | index + N 个页面 | 0-1 个新页面 | 2 个文件 | 按复杂度 |
| Lint | 全量扫描 | 矛盾标注、修复链接 | 全库 | 全库 |

## 4. Ingest 编译管线详解

Ingest 是 LLM Wiki 最核心的操作。以下是从触发到完成的完整 6 阶段流程。

### 阶段 0：触发条件

进入 Ingest 模式的信号：

- 用户显式指令：`"处理 raw/ 中的新文件"` / `"帮我灌入这个论文"` / `"Ingest this"`
- 系统扫描发现：raw/ 目录中有 index.md 或 log.md 中未登记的新文件
- **硬约束**：一次只处理一份——妥协了质量就会崩

### 阶段 1：理解与分类 (Understand)

拿到 raw 文件后，通读全文，完成三项判定：

**1.1 判定资料类型**

| 类型 | 特征 | 影响编译策略 |
|------|------|-------------|
| 论文 | 摘要 + 方法 + 实验 + 结论 | 侧重方法论和实验数据 |
| 技术博客 | 叙事性 + 示例 + 意见 | 侧重观点和实践经验 |
| 会议纪要 | 时间线 + 决定 + 行动项 | 侧重决策链和上下文 |
| 个人笔记 | 随意格式 + 主观标注 | 侧重知识连接和个人洞察 |

**1.2 提取元信息**

- 作者（姓名 + 机构）
- 发表/创建时间
- 来源链接（URL、arXiv ID 等）
- 相关项目或代码库

**1.3 顶级主题判断**

"这份资料是关于什么的？"——这个判断决定 `topics/` 层面创建/更新什么。例如：
- "Attention Is All You Need" → `topic-seq2seq-modeling`
- 一篇关于 Mamba 的文章 → `topic-state-space-models`

### 阶段 2：实体识别与分类 (Classify)

这是整个管线中"编译感"最强的环节。不是传统的 NER 工具链，而是用 LLM 的语义理解能力做分类：

```
扫描文中出现的所有命名实体和抽象概念：

识别到人物姓名 + 贡献
  → entities/person-xxx
  → 判断：此人在该资料中的核心贡献是什么？

识别到公司/机构 + 隶属关系
  → entities/company-xxx
  → 判断：该机构在此研究中的角色（资助方？合作方？竞争对手？）

识别到产品/系统/框架名称
  → entities/product-xxx
  → 判断：该产品处于什么版本？有何关键特性？

识别到理论概念（"是什么"）
  → concepts/concept-xxx
  → 判断：这是新概念的首次定义，还是对已有概念的引用？

识别到可操作的方法论（"怎么做"）
  → concepts/method-xxx
  → 判断：该方法是否有可量化的效果数据？
```

**concept vs method 的区分逻辑**：

```
问自己：这个页面 80% 的内容是在解释"定义和原理"还是"步骤和参数"？

定义和原理 → concepts/concept-xxx
步骤和参数 → concepts/method-xxx

例子：
- Self-Attention: 解释 Q/K/V 的含义和作用 → concept
- Multi-Head Attention: 描述头数选择、维度分割、拼接算法 → method
```

### 阶段 3：页面撰写 (Compose)

对阶段 2 识别出的每个实体/概念，逐个处理。

**3.1 创建 vs 更新的判断**

```
读取 index.md → 检查目标页面是否存在

不存在 → CREATE 模式：
  - 按完整模板创建新页面
  - 写摘要 + 详情 + 关联 + 引用来源 + 变更记录
  - 在变更记录中标注 "初始创建，来源 [[raw/xxx]]"

已存在 → APPEND 模式：
  - 先 Read 已有页面内容（必须！）
  - 在详情部分追加新内容（用子标题区分历史内容和新内容）
  - 在关联部分追加新的交叉引用
  - 在变更记录中标注 "YYYY-MM-DD: 更新 XXX 部分，来源 [[raw/yyy]]"
  - **绝不覆盖或删除历史内容**
  - 更新 "最后更新" 时间戳
```

**3.2 页面撰写的质量检查清单**

在保存每个页面前，自我检查：

- [ ] 摘要是否真正概括了核心内容（而非复制标题）？
- [ ] 每个事实性陈述是否有对应的 `[[raw/xxx]]` 引用？
- [ ] 关联部分是否列出了所有已知的相关实体和概念？
- [ ] 交叉引用是否是双向的（如果 A 链了 B，B 也应该链 A）？
- [ ] 变更记录是否包含日期、动作描述和来源？

### 阶段 4：矛盾检测 (Conflict Check)

这是 LLM Wiki **区别于普通 RAG 的关键环节**。

**4.1 检测流程**

```
For 每个被更新或创建的页面 P:
  For 每个被 P 引用的已有页面 Q:
    1. 读取 Q 的完整内容
    2. 提取 Q 中所有的"事实性声明"（排除观点和推理）
    3. 将 P 的新声明与 Q 的旧声明逐条比对
    4. 如有矛盾 → 跳转到标注流程
```

**4.2 矛盾标注规范**

```markdown
> ⚠️ 矛盾标注：{一句话描述矛盾点}
> 
> [[wiki/concepts/concept-xxx]] 中记载：{旧的说法}  
> （来源：[[raw/older-source.md]]）
> 
> [[wiki/concepts/concept-yyy]]（本文）记载：{新的说法}  
> （来源：[[raw/newer-source.md]]）
> 
> 可能原因：{LLM 的推测分析，标注为 AI 推理}
> 建议：人工核实两篇原始资料的具体数据和实验设置。
```

**4.3 矛盾标注的原则**

- 标注时**同时在两个页面上**插入标注块
- 明确区分"原始资料的直接记载"和"LLM 的推测分析"
- 绝不自动消解矛盾——AI 无权替用户做价值判断
- 使用 markdown blockquote 格式使其在渲染时视觉上突出

### 阶段 5：更新 index.md

**操作**：

1. 遍历 `wiki/entities/`、`wiki/concepts/`、`wiki/topics/` 三个目录
2. 统计每个目录下的页面数量
3. 对新页面：添加一行 `- [[relative-path]] — 简短描述`
4. 更新顶部元数据：`> 总页面数: {N} | 最后更新: YYYY-MM-DD`

**原则**：

- index.md 是**唯一导航入口**——任何不在此文件中的页面等于不存在
- 简短描述控制在 15 字以内，给出最核心的定位
- 按字母序排列（同名页面时）

### 阶段 6：追加 log.md

**格式**：按日期组织，每年一个 `## YYYY` 二级标题

**条目类型**：

| 前缀 | 含义 | 示例 |
|------|------|------|
| ✨ 新增 | 创建了全新页面 | `✨ 新增: [[entities/person-vaswani]] — 来源 [[raw/attention-paper]]` |
| 📝 更新 | 增量修改了已有页面 | `📝 更新: [[concepts/self-attention]] — 新增了多头注意力的变体讨论` |
| 🔗 链接 | 建立了新的交叉引用 | `🔗 链接: [[entities/google-brain]] ↔ [[concepts/transformer]]` |
| ⚠️ 矛盾 | 发现了知识冲突 | `⚠️ 矛盾: [[concepts/training-data]] 与 [[concepts/scaling-law]] 在数据量上存在分歧` |

**log.md 的信任根角色**：

- 它是知识库的 "git log"——完整、不可变、可审计
- 如果 index.md 损坏或丢失，可以从 log.md 重建索引
- 每次 Ingest 完成后，log.md 追加的条目数应等于实际变更的页面数

## 5. 扇出结构：一份 raw 如何变成 10-15 个页面

以一篇典型论文为例，展示编译后的页面分布：

### 输入

```
raw/paper-attention-is-all-you-need.md  （一份 Transformer 论文）
```

### 输出（预计 10-15 个页面）

#### entities/（4-6 个页面）

| 页面 | 类型 | 内容 |
|------|------|------|
| `person-vaswani` | 人物 | Ashish Vaswani 的学术贡献和后续工作 |
| `person-shazeer` | 人物 | Noam Shazeer 的贡献（SwiGLU 等后续工作） |
| `person-parmar` | 人物 | Niki Parmar 的贡献 |
| `company-google-brain` | 机构 | Google Brain 团队在该时期的研究方向 |
| `company-google-research` | 机构 | Google Research 的相关工作 |
| `product-tensor2tensor` | 产品 | 论文使用的训练框架 |

#### concepts/（4-5 个页面）

| 页面 | 类型 | 内容 |
|------|------|------|
| `concept-self-attention` | 理论 | Self-Attention 的定义、QKV 的含义、计算复杂度 |
| `method-multi-head-attention` | 方法 | 多头注意力的实现细节、头数选择、维度分割 |
| `concept-positional-encoding` | 理论 | 位置编码的必要性、正弦编码的数学形式 |
| `concept-layernorm` | 理论 | Layer Normalization 的原理 |
| `method-residual-connection` | 方法 | 残差连接的具体实现方式 |

#### topics/（2-3 个页面）

| 页面 | 类型 | 内容 |
|------|------|------|
| `topic-seq2seq-modeling` | 综述 | 序列到序列建模的发展脉络 |
| `comparison-transformer-vs-rnn` | 对比 | Transformer 与 RNN/LSTM 的横评 |
| `topic-neural-machine-translation` | 综述 | 神经机器翻译的技术演进 |

### 扇出分布规律

```
一份 raw 论文典型的页面分布：
┌──────────────┬──────┬──────────────────────────────┐
│ 目录         │ 页面数│ 说明                          │
├──────────────┼──────┼──────────────────────────────┤
│ entities/    │ 4-6  │ 作者约 2-4 人，机构 1-2 个     │
│ concepts/    │ 4-5  │ 核心概念 + 关键方法             │
│ topics/      │ 2-3  │ 1 个领域综述 + 可选对比         │
│ index.md     │ 1    │ 更新（非新页面）                │
│ log.md       │ 1    │ 追加（非新页面）                │
├──────────────┼──────┼──────────────────────────────┤
│ 总计接触     │ 12-16│ 含新创建 + 更新                │
└──────────────┴──────┴──────────────────────────────┘
```

实际情况会因资料复杂度浮动：
- 一篇简单技术博客 → 可能只接触 5-8 个页面
- 一篇综述论文 → 可能接触 15-20 个页面

## 6. 设计预设 (Assumptions)

这些预设不是凭空来的，而是为了一套知识管理哲学服务的——**编译一次，持续保鲜"**。

### A1: raw 不可变

```
原始资料放入 raw/ 后永不修改。
```

**理由**：保证知识溯源的完整性。你可以回头看"当时我是怎么理解的"，而不会因为后续修改污染了原始记录。如果对同一主题有了新理解，应该添加新的 raw 文件，让两个版本并存。

### A2: 固定实体粒度

```
实体：人 / 公司 / 产品（三级）
概念：理论 / 方法（两级）
主题：综述 / 对比（两级）
```

**理由**：粒度太细会碎片化到无法导航（100 个 person 页面很少有交叉引用），太粗会信息过载（一个"AI"页面试图涵盖所有内容）。三级/两级在实践中恰好平衡。

### A3: 页面只增不删

```
页面创建后从不删除，历史内容保留，新内容追加。
```

**理由**：知识演化需要可追溯。你可以看到一个概念的理解如何随时间深化——从最初读到的论文摘要，到后来的补充研究，再到实践中获得的经验。这本身就是有价值的知识资产。

### A4: index.md 是唯一导航入口，log.md 是唯一信任根

```
index.md：所有页面必须在其中注册，否则视为不存在
log.md：完整的时间线记录，不可篡改，可从日志重建索引
```

**理由**：
- index.md 防止"知道的页面找不到"——这是搜索可用性的底线
- log.md 提供可审计性——"这条信息是什么时候、从哪个来源进入知识库的？"

### A5: 编译质量优先于速度

```
一次只处理一份 raw 资料。不批量处理。
```

**理由**：编译质量靠深度理解，不是靠吞吐量。10 份 raw 分 10 次处理，每次建立深度交叉引用，远好过一次全灌。因为每次 Ingest 会改变 Wiki 的状态，后续 Ingest 可以基于更丰富的上下文。

### A6: 矛盾不自动消解

```
发现矛盾时只标注，不判断谁对谁错。
```

**理由**：两个权威来源打架时，AI 无权替你做价值判断。标注出来让人类决策——谁的数据更新？谁的实验设置更合理？谁有利益冲突？这些判断需要上下文和人类判断力。

### A7: SCHEMA.md 是宪法

```
所有格式规范、命名约定、目录结构由 SCHEMA.md 定义。
所有 Ingest/Query/Lint 操作都遵守 SCHEMA.md。
```

**理由**：未来换一个 LLM 模型执行 Ingest，只要加载同一份 SCHEMA.md，产物格式一致。这是跨模型兼容性的保证。

### A8: Wiki 是"活的"（隐式预设）

```
知识库不会某天"完成"，而是一直在生长。
```

**理由**：这也是为什么强调增量更新、不删页面、矛盾标注——这些设计都是为"持续生长"准备的，而非一次性项目。一个好的 Wiki 会随着时间变得更有价值，而不是更臃肿。

## 7. 关键设计决策：RAG vs LLM Wiki

### RAG 模式

```
查询时：检索 → 排序 → 注入上下文 → 生成答案 → 答案只存在于对话历史中
下次查询：重新检索 → 重新排序 → 重新注入 → 重新生成
```

**问题**：
- 每次查询从零开始，无持久洞察
- 交叉引用不积累——两次查询不能互相受益
- 无法发现和标记知识矛盾
- 对话历史丢失 = 知识丢失

### LLM Wiki 模式

```
编译时：读取 raw → 提取实体/概念 → 结构化为页面 → 建立交叉引用 → 标记矛盾
查询时：读 index → 定位页面 → 基于已编译的知识回答 → 答案归档 → 知识持续增长
```

**优势**：

| 维度 | RAG | LLM Wiki |
|------|-----|----------|
| 知识持久性 | 无（只在对话历史） | 有（Markdown 文件系统） |
| 交叉引用 | 无 | 双向 wiki-link 自动建立 |
| 矛盾检测 | 无 | 跨页面比对 + blockquote 标注 |
| 增量学习 | 每次从零开始 | 追加新内容到已有页面 |
| 可审计性 | 无 | log.md 完整时间线 |
| 跨模型兼容 | 依赖向量嵌入 | 纯 Markdown，任何 LLM 可读 |
| 人工可读 | 否 | 是（标准 Markdown 文件） |

### 本质区别

```
RAG = 查询时编译（每次重建临时索引）
LLM Wiki = 编译时处理（一次性建立持久结构）

类比：
RAG    像是每次做饭都去菜市场现买
LLM Wiki 像是建立了一个储备充足的厨房 + 食谱库
```

## 8. 知识复利飞轮

```
         Ingest 扩大知识面
              │
              ▼
     Wiki 交叉引用密度上升
              │
              ▼
     Query 命中率 + 答案质量提升
              │
              ▼
     高质量答案被归档为新页面
              │
              └──── 循环 ────┘
```

### 可量化的增长指标

1. **交叉引用密度**：每个页面的 `## 关联` 部分的 `[[wiki-link]]` 数量。初始可能只有 1-2 个，随着 Ingest 次数增加，应有 5+ 个。
2. **矛盾标注数量**：随着知识库扩大，矛盾自然出现。矛盾标注数量应增长，但质量应保持（非虚假矛盾）。
3. **索引完整性**：所有 wiki/ 下的 .md 文件都应在 index.md 中注册。100% 是最低标准。
4. **查询命中率**：用户提问时，能在多少比例的情况下在 Wiki 中找到直接相关的页面。

### 飞轮效应的临界点

```
初期（0-5 次 Ingest）：
  - 页面少，交叉引用稀疏
  - 查询命中率低
  - 飞轮尚未启动

中期（10-30 次 Ingest）：
  - 交叉引用密度达到 3-5 个/页面
  - 查询命中率 > 50%
  - 飞轮开始自转——每次查询都能发现新的连接

成熟期（50+ 次 Ingest）：
  - 矛盾标注出现（多个来源覆盖同一主题）
  - 查询时经常触发"这个答案值得归档"的判断
  - Wiki 成为真正的外部大脑
```

## 9. 质量保证机制

### 9.1 Never Hallucinate 的实现

**硬约束**：
- 所有事实性陈述必须有 `[[raw/xxx]]` 引用
- 如果某句话来自 AI 的综合推理而非原始资料，明确标注"（AI 推理）"
- 不确定的信息用"可能"、"据推测"等限定词

**反例**：
```markdown
❌ Transformer 使用了 12 层编码器。
   没有来源标注，无法知道 12 这个数字从何而来。

✅ Transformer 的 base 模型使用了 6 层编码器，big 模型使用了 6 层。
   来源：[[raw/paper-attention-is-all-you-need.md]]
   （注：AI 推理——该论文在摘要中说明，实际描述的是 6 层）
```

### 9.2 Always Cite 的实现

每个页面有两个引用层次：

1. **页面级引用**：`> **来源**: [[raw/source-file]]` —— 指明该页面的主要信息来源
2. **段落级引用**：`[1] [[raw/paper-xxx.md]] — 第 3.2 节关于 Multi-Head Attention 的定义`

查询回答时的引用要求：
```
答案：Transformer 的核心创新是用 Self-Attention 替代循环结构。
来源：[[concepts/concept-self-attention]]，其中引用了 [[raw/attention-paper]]
```

### 9.3 Mark Conflicts 的实现

参见 [阶段 4：矛盾检测](#阶段-4矛盾检测-conflict-check)。

核心要义：
- 标注在**两个页面**上都出现
- 区分事实记载和 AI 推测
- 不自动消解
- 使用统一的 blockquote 格式

### 9.4 Incremental Updates 的实现

```markdown
## 详情

### 初始理解（2024-01-15，来源 [[raw/paper-v1]]）
{第一次读到这个概念时的理解}

### 补充理解（2024-03-20，来源 [[raw/paper-v2]]）  
{后来读到相关资料后的补充}

### 实践洞察（2024-06-10，来源 [[raw/personal-notes]]）
{在实际使用中的经验和反思}
```

时间维度成为知识结构的一部分——你不仅知道"是什么"，还知道"什么时候开始这样想的"。

## 10. 总结

LLM Wiki 的本质是用**编译时的深度加工**替代**查询时的浅层检索**。它不是又一个 RAG 方案，而是一种不同的知识管理哲学：

```
RAG 的世界观：知识在原始文档中，每次查询时临时提取
LLM Wiki 的世界观：知识需要"编译"才能增值，编译后的产物本身就是知识资产
```

我的实现由两层组成：
- **Expert Prompt**（灵魂）：定义"我是谁"——价值观、质量标准、工作流程
- **llm-wiki Skill**（手册）：提供具体指令——路径、脚本、触发匹配

我操作三层数据：
- **raw/**（不可变原始层）→ **wiki/**（编译知识层）→ **SCHEMA.md**（规则宪法）

我执行三种操作：
- **Ingest**（知识编译，6 阶段管线）
- **Query**（知识检索，飞轮驱动）
- **Lint**（健康巡检，质量守护）

最后，我的 8 个核心预设（raw 不可变、固定粒度、只增不删、index 是入口、log 是信任根、质量优先、矛盾标注不消解、SCHEMA 是宪法）构成了这套系统的**设计约束**——它们不是我随意定的，而是为了一个目标：让知识库像复利一样持续增值。
